# 익명 집계 통계 설계안 (구현 전 · 검토용)

작성 2026-09-05. **이 문서는 설계만 담는다. 구현하지 않았다.**

## 왜 하려는가

가이드는 지금 "2~3주" 같은 소요 기간을 **추정치로** 적고 있다. 실제로 해본 사람들의 분포를 보여줄 수 있다면 그 숫자가 근거를 갖는다. 학생 입장에서도 "나만 오래 걸리나?" 하는 불안이 줄어든다.

이미 [lib/activity.ts](../lib/activity.ts)가 단계별 첫 활동·마지막 활동·달력 소요일수를 **브라우저 안에서** 계산하고 있다. 보낼 데이터는 이미 만들어져 있고, 보내는 경로만 없는 상태다.

## 넘지 않을 선

이 사이트는 [/privacy](../app/privacy/page.tsx)와 [/about](../app/about/page.tsx)에서 **"서버로 전송되지 않고, 저희도 볼 수 없습니다"**라고 공개적으로 약속했다. 주 사용자는 청소년(미성년자)이다. 국내법상 만 14세 미만은 개인정보 수집에 법정대리인 동의가 필요하다.

따라서 이 기능은 아래를 **모두** 만족할 때만 켠다.

1. **개인정보를 수집하지 않는다.** 식별자(계정·기기 ID·쿠키·IP 기반 지문)를 만들지 않는다.
2. **자유 서술 텍스트를 보내지 않는다.** 메모·연구질문·설문 문항은 개인정보가 섞일 수 있으므로 전송 대상에서 제외한다.
3. **명시적 opt-in.** 기본값은 꺼짐. 사용자가 직접 켜야 한다.
4. **방침 문서를 먼저 고친다.** 코드보다 문서가 먼저다.
5. **끌 수 있고, 껐다는 사실이 즉시 반영된다.**

이 중 하나라도 못 지키면 기능을 만들지 않는다.

## 보낼 것 / 안 보낼 것

| 항목 | 전송 | 근거 |
| --- | --- | --- |
| 단계 slug + 완료까지 걸린 달력 일수 | O | 숫자 2개. 개인 식별 불가 |
| 체크리스트 항목 완료 여부(항목 문구 아님, 인덱스) | O | 어느 항목에서 오래 멈추는지 파악 |

| 학교급(중/고/기타) | △ | 표본이 작을 때 재식별 위험. **1단계에서는 제외** |

| 타임스탬프(정확한 시각) | X | 접속 패턴이 준식별자가 된다. **날짜 단위로 절삭** |
| IP·User-Agent | X | 서버에서 **기록하지 않도록** 명시적으로 끈다 |

## 전송 시점

세션마다 보내지 않는다. **단계를 완료한 순간 1회**만 보낸다.

- 중복 전송 방지: 브라우저에 `research-guide:stats-sent:{stage}` 플래그를 남긴다. 같은 기기에서 재전송하지 않는다.
- 플래그는 localStorage라 지워질 수 있다. 중복이 일부 생기는 것은 감수한다 — 정확도보다 무식별이 우선이다.

## 저장소

세 후보를 비교했다.

| 후보 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| Vercel KV (Upstash Redis) | 배포처와 같은 곳, 설정 최소, 카운터 증가에 최적(`INCR`) | 무료 티어 한도 | **1순위** |
| Supabase | SQL, 대시보드 | 이 용도에 과함, 테이블·정책 설계 부담 | 보류 |
| 파일 + GitHub Actions | 비용 0 | 쓰기 지연·경쟁 상태 | 부적합 |

집계는 **카운터와 히스토그램 버킷**만 쓴다. 원자료(row)를 저장하지 않으면 재식별 위험이 구조적으로 사라진다.

```
stage:{slug}:days:{bucket}   → INCR      # 버킷 = 1-3, 4-7, 8-14, 15-28, 29+
stage:{slug}:completed       → INCR
design:{type}                → INCR
tool:{id}:used               → INCR
```

버킷으로 저장하면 개별 값이 남지 않아, 데이터가 유출돼도 특정인을 지목할 수 없다.

## API 설계

`POST /api/stats` (신규)

```
요청  { "kind": "stage-complete", "stage": "topic", "daysBucket": "4-7" }
응답  204 No Content
```

- **입력 검증이 방어선이다.** stage는 STAGE_SLUGS 화이트리스트, daysBucket은 정해진 5개 문자열, kind는 정해진 집합. 그 외는 400으로 버린다. 자유 문자열을 받는 필드를 만들지 않는다.
- 응답 본문을 주지 않는다(204). 읽기 API는 따로 두지 않고, 집계 결과는 **빌드 타임에 읽어 정적 페이지로** 굽는다 — 그래야 런타임 비용과 어뷰징 표면이 함께 사라진다.
- 레이트리밋: 같은 IP에서 분당 N회 초과 시 무시. **IP는 카운트에만 쓰고 저장하지 않는다.**
- CORS: 같은 오리진만.

## opt-in UX

- 위치: 가이드 목록의 &lsquo;내 기록&rsquo; 섹션(이미 내보내기·백업·삭제가 모여 있는 자리).
- 문구는 무엇을 보내는지 **구체적으로** 적는다. "익명 통계 수집에 동의" 같은 뭉뚱그린 표현을 쓰지 않는다.
  - 예: "단계를 끝낼 때마다 *어느 단계인지*와 *며칠 걸렸는지(구간)*만 보냅니다. 메모·연구질문·이름은 보내지 않습니다."
- 기본값 꺼짐. 끄면 이후 전송이 즉시 멈춘다(이미 보낸 집계는 되돌릴 수 없다는 점도 명시).

## 방침 문서 개정

구현 **전에** 아래를 고친다.

- `/privacy`: "서버로 전송되지 않습니다" → 기본 동작은 그대로이되, opt-in 시 전송되는 항목·목적·보관 형태(집계 카운터)를 별도 절로 추가.
- `/about`의 "여러분의 기록은 어디에 저장되나" 문단도 같은 취지로 수정.
- 두 문서가 서로 어긋나면 안 된다. 같은 문장을 쓸 것.

## 롤아웃 순서

1. 방침 문서 개정 → 배포
2. `/api/stats` + 저장소 연결, opt-in UI (기본 꺼짐)
3. 2주간 데이터가 실제로 쌓이는지, 이상 트래픽이 없는지 관찰
4. 표본이 **단계당 30건 이상** 모인 항목만 화면에 노출. 그 전에는 아무것도 보여주지 않는다 — 표본 5건으로 "평균 3주"를 보여주면 틀린 정보다
5. 노출 시 항상 표본 수를 함께 적는다("42명 기준")

## 중단 조건

아래 중 하나라도 발생하면 기능을 끄고 재검토한다.

- 재식별 가능성이 제기됨
- 어뷰징으로 집계가 오염됨
- 애드센스·법적 이슈가 제기됨
- 표본이 3개월간 단계당 30건에 못 미침 (가치가 없다는 뜻)

## 지금 하지 않는 이유

애드센스 재검토가 진행 중이다. 심사 중에 데이터 수집 기능이 새로 생기면 심사자가 보는 사이트의 성격이 달라진다. **심사 결과가 나온 뒤에 1번(방침 개정)부터 시작한다.**
