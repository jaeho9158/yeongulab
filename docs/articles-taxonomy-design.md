# 자료실 확장 설계안 — 5축 콘텐츠를 /articles 하나로 통합

작성 2026-09-05. **설계만 담는다. 코드는 바꾸지 않았다.**

> **후속 문서:** 글별 설계·보강·지원 코드·실행 순서는 [articles-content-plan.md](articles-content-plan.md)에 있다. 두 문서가 어긋나면 content-plan이 우선한다(기존 8편 order·featured 값 포함).

## 결정: 새 섹션을 만들지 않고 자료실을 넓힌다

제안된 5축(주제탐구·실전 노하우·워크플로우·선행연구 검색·대외활동)을 별도
라우트로 쪼개지 않고 `/articles` 안에 **카테고리**로 넣는다.

이유는 세 가지다.

1. **내부 링크가 이미 자료실로 모인다.** 홈·가이드 목록·단계 페이지·도구
   색인·소개·푸터 6곳이 `/articles`를 가리킨다. 새 섹션을 파면 이 링크
   자산을 나누는 셈이다.
2. **파이프라인이 그대로 쓰인다.** `lib/articles.ts` → 목록·상세·사이트맵·
   OG 이미지·JSON-LD·단계 역링크가 전부 `getAllArticles()` 하나에 매달려
   있다. 파일 하나 추가하면 그 여섯이 자동으로 따라온다.
3. **카테고리 라우트는 얇은 페이지다.** `/articles/topic` 같은 페이지를
   만들면 글 5~7편 링크만 있는 페이지가 넷 생긴다. 애드센스 재검토 중에
   일부러 만들 이유가 없다. 목록 페이지 안의 앵커(`#topic`)로 충분하다.

## 카테고리 — 5축이 아니라 4개

제안된 5축을 그대로 쓰지 않는다. 기존 8편까지 같이 분류해보면 **가이드
단계 흐름에 맞춘 4개**가 더 자연스럽다.

| key | 이름 | 기존 글 | 신규 (제안 목록에서) |
| --- | --- | --- | --- |
| `topic` | 주제 잡기 | 06 주제 48가지 | Discussion에서 주제 뽑기 · 진부해지는 이유 · 궁금 vs 탐구 가능 · 교과→탐구 4경로 · 재현 연구 · 끝낼 수 있는 크기 · 공공데이터 설계 (7) |
| `search` | 선행연구 찾고 읽기 | 05 영어 논문 | PubMed · RISS/KCI · 전문 무료 접근 · 리뷰 논문부터 · 인용 따라가기 · Figure만 보고 주장 · Methods 빌리기 · Scholar 알림 (8) |
| `method` | 설계와 데이터 | 02 설문 문항 · 04 윤리 | 대조군 오류 · 표본 부족 · 질문→가설→검증 · 실험 노트 · 아카이빙 규칙 (5) |
| `writing` | 쓰기와 발표 | 03 통계 · 07 발표 · 08 초록 | 음성 결과 쓰기 · Limitation · 공고 찾는 법 (3) |

FAQ(01)는 카테고리 없이 **목록 맨 위에 고정**한다. 여러 축에 걸치는 글이라
어느 하나에 넣으면 나머지에서 안 보인다.

제안 3축(옵시디언·Zotero·Dataview)은 **카테고리를 만들지 않는다.** 나중에
쓰더라도 1편이고, 1편짜리 카테고리는 빈 서랍처럼 보인다. 쓰게 되면
`method`에 넣는다.

제안 5축(대외활동 캘린더)은 "공고 찾는 법" 1편으로 줄여 `writing`(제출)에
둔다. 분기별 갱신 캘린더는 만들지 않는다 — 낡는 순간 학생이 마감을 놓치는
해악이 되고, 갱신 약속이 끝나지 않는다.

### 왜 relatedStage에서 파생하지 않는가

카테고리 4개가 단계 6개를 2:1로 묶은 모양이라 `relatedStage → category`
매핑으로 자동 도출할 수 있어 보인다. 하지만 안 한다.

- `relatedStage`는 선택 필드다. 없는 글은 분류가 사라진다.
- "Figure만 보고 주장 파악"은 `prior-research` 단계에 걸리지만, 읽는
  기술이므로 `search`에 있어야 한다. 반대로 "표본이 부족할 때"는
  `data-collection`에 걸리지만 설계 판단이라 `method`다. 1:1이 아니다.
- 매핑 표는 영리하지만 불투명하다. frontmatter에 한 줄 더 쓰는 쪽이 글을
  쓰는 사람에게 명시적이다.

## 스키마 변경

`content/articles/*.mdx` frontmatter에 두 필드를 더한다.

```yaml
category: topic        # 필수. topic | search | method | writing. FAQ만 생략
featured: true         # 선택. 홈에 노출할 글. 기본 false
```

`lib/articles.ts`:

```ts
export const ARTICLE_CATEGORIES = {
  topic:   { label: "주제 잡기",          intro: "..." },
  search:  { label: "선행연구 찾고 읽기", intro: "..." },
  method:  { label: "설계와 데이터",      intro: "..." },
  writing: { label: "쓰기와 발표",        intro: "..." },
} as const;
export type ArticleCategory = keyof typeof ARTICLE_CATEGORIES;

type Article = {
  // ...기존
  category?: ArticleCategory;   // FAQ만 undefined
  featured: boolean;
};
```

- `readArticleFile`에서 `category`가 enum 밖이면 **빌드 때 throw**한다.
  오타가 조용히 "분류 없음"으로 빠지면 목록에서 사라지는데, 아무도
  모른다. `stageToolMeta.ts`의 `satisfies` 패턴과 같은 취지.
- `order`는 **카테고리 안에서의 순서**로 의미가 바뀐다. 전역 순서는
  카테고리 순 → order 순으로 정렬해 얻는다. 기존 8편은 order를 다시
  매긴다(카테고리별 1부터).
- 새 함수: `getArticlesByCategory(): Record<ArticleCategory, Article[]>`,
  `getFeaturedArticles(limit)`.

## 화면별 변경

### `/articles` 목록

지금은 8편 평면 목록. 28편이 되면 스크롤 한 화면을 넘긴다.

- FAQ를 맨 위에 카드로 고정("먼저, 자주 막히는 질문 24가지").
- 아래에 카테고리 4개를 `<section id={key}>`로 나눈다. 각 섹션에 h2
  라벨과 intro 한 문장. 그 안은 지금과 같은 괘선 목록.
- 섹션 h2 앞에 카테고리 앵커를 가로로 나열한 미니 목차를 둔다
  (`nav-scroll` 클래스 재사용, 좁은 화면에서 가로 스크롤).
- 두 자리 번호는 유지하되 카테고리 안 번호가 된다.

### `/articles/[slug]` 상세

- 지금 "다른 글" 3편은 `articles.filter(...).slice(0, 3)` — 전체에서
  앞 3편이라 모든 글이 같은 3편을 추천한다. **같은 카테고리 우선**, 모자라면
  다른 카테고리로 채운다.
- 같은 카테고리 안에서 **이전/다음 글** 링크를 단계 페이지처럼 하단에 둔다.
  카테고리가 사실상 읽기 순서이기 때문이다(예: 리뷰 논문부터 → 인용
  따라가기 → Figure만 보고 → Methods 빌리기).
- 상단 "← 자료실" 링크는 `/articles#${category}`로 돌아간다.
- 빵부스러기(JSON-LD)는 홈 › 자료실 › 글 그대로. 카테고리 라우트가 없으니
  넣지 않는다.

### 홈

지금은 `articles.map(...)`로 **전부** 나열한다. 28편이면 홈이 목록 페이지가
된다. `featured: true`인 글만 **최대 6편**. 6편은 카테고리당 1~2편으로
고른다. "자료실 전체 →" 링크는 그대로.

### 단계 페이지 "이 단계와 함께 읽기"

`getArticlesForStage`는 그대로. 다만 `topic` 단계가 8편까지 붙을 수 있다.
전부 보여준다 — 이 목록은 그 단계에 있는 사람을 위한 것이라 잘라낼 이유가
없다. 레일 카운트도 그대로 맞는다.

### 바뀌지 않는 것

사이트맵·OG 이미지·JSON-LD·`/tools` 역링크. 전부 `getAllArticles()`를
읽으므로 파일만 추가하면 된다.

## 기존 글 보강 5건 (새 페이지 대신)

| 제안 항목 | 넣을 곳 | 방식 |
| --- | --- | --- |
| t-test와 ANOVA 사이 | 03 통계 | "검정 고르기" 절에 선택 흐름 표 추가 |
| 논문 읽는 순서 | 05 영어 논문 | 첫 절을 순서 중심으로 재정리 |
| 포스터 3미터 · 심사위원이 보는 것 | 07 발표 | 포스터 절 확장 + 심사 기준 절 신설 |
| 초록 250자 | 08 초록 | 6문장 템플릿 뒤에 압축 예시 추가 |
| 단원별 확장 지도 | 06 주제 48 | Round 3 분야별 글로 링크 |

보강한 글은 `updated`를 올린다. JSON-LD `dateModified`가 그걸 읽는다.

## 함정 (구현할 때)

- **OG 서브셋 폰트.** `lib/__tests__/ogFont.test.ts`가 모든 글 제목의
  글자를 검사한다. 신규 제목에 새 한글이 들어가면 실패한다 — 이건 버그가
  아니라 설계된 경보다. 라운드마다 `assets/fonts` 재생성이 필요하다.
- **relatedStage 균형.** 지금 `topic` 단계에 글이 몰린다. 단계당 최대 8편
  정도면 괜찮지만, 그 이상이면 단계 페이지 하단이 길어진다.
- **홈의 `featured` 누락.** 아무 글도 featured가 아니면 홈 섹션이 빈다.
  `getFeaturedArticles`는 featured가 0편이면 카테고리별 첫 글로 대체한다.
- **order 재매김은 URL을 바꾸지 않는다.** slug가 URL이고 order는 표시
  번호일 뿐이라 색인된 주소는 그대로다.

## 롤아웃

코드 변경은 **한 번**, 콘텐츠는 라운드로.

1. 스키마 + 목록/상세/홈 개편 + 기존 8편 frontmatter 이관 → 빌드·테스트 →
   배포. 이 시점엔 글이 8편 그대로라 화면은 카테고리 4개에 1~3편씩.
2. Round 3: `search` 8편 (차별화 최상이라 먼저) + 보강 2건
3. Round 4: `topic` 7편 + 보강 2건
4. Round 5: `method` 5편 + `writing` 3편 + 보강 1건
5. 라운드마다: 폰트 재생성 → 빌드 → 색인 요청(일일 할당량 안에서)

1단계를 먼저 배포하는 이유: 구조 변경과 콘텐츠 추가를 한 커밋에 섞으면
목록이 깨졌을 때 원인을 못 가른다.

## 열어둔 것

- **시리즈.** "논문 읽기" 3편(순서·Figure·Methods)은 연작이다. `series`
  필드로 묶어 상세 하단에 "이 시리즈" 박스를 둘 수 있다. 지금은 카테고리
  안 이전/다음으로 충분하다고 보고 미룬다. 연작이 두 개 이상 생기면 그때.
- **옵시디언 1편.** 쓸지 말지는 운영자 결정. 쓰면 `method`, 실제 볼트 기준.
- **탐구 파일 반영.** 운영자 실제 연구 파일이 들어오면 `search`·`method`의
  실전 글에 사례로 녹인다. 익명화 범위는 별도 확인.
